# Experience OS：产品定义与竞品调研

日期：2026-07-26  
结论强度：产品定位判断，不是市场份额或商业收入预测。

## 1. 先说人话：EOS 到底是什么

**EOS 是一个把人和 AI 的协作，转化为“可追溯、经人确认、被结果验证、能在下次复用”的经验的本地系统。**

它不是第二个 Codex，不负责替人写代码；也不是第二个聊天记录库，不主张把所有对话保存下来。它处在各种 AI 工具之上，负责一件更窄但更关键的事：

> 把一次协作中真正值得留下的做法，变成下一次可以被安全调用的经验，而不是一段没人再看的聊天记录。

最小闭环是：

`人明确同意的协作片段 -> 工作节点与来源证据 -> AI 提出经验草案 -> 人确认/改写/暂缓 -> 观察实际结果 -> 仅将成功且有边界的内容升级为可复用经验`

其中的中心功能不是“Skill”，甚至不是“记忆”。它是 **Experience Receipt（经验收据）**：一份说明“做了什么、为什么值得记、证据来自哪里、适用在哪里、还没有证明什么”的受控记录。Skill、规则、偏好、工作流、提示词都只是经验的不同投影或使用形态。

## 2. 为什么它仍然符合“解放人”的初衷

原始理念里的“自动化”是对的，但需要更准确地分配自动化：

- 自动化：识别可能值得沉淀的节点、生成收据草案、寻找相似已验证经验、提示下一步。
- 人类决定：是否允许保存原文、草案是否符合事实、结果是否真的成功、经验是否应跨项目复用。

因此 EOS 不该让人手动找 Skill、手动装 Skill、手动维护复杂知识库；它应该让人只在**不能外包的判断点**按一次确认。严格许可不是反自动化，而是防止“自动记忆”把隐私、误解和噪声永久化。

一句更准确的产品承诺是：

> **让 AI 自动替你整理候选经验，让你只负责确认什么是真的、什么有用。**

## 3. 今天已经具备什么

当前 EOS 已经是可运行的 Alpha，而非只有概念：

1. 每个工作区可 Bootstrap 出独立的 `.eos/`、本地 Git Vault、README 和 MCP 配置，不扫描或搬动业务文件。
2. 支持 MCP 接入；外部 Agent 的捕获默认必须经过一次性、内容哈希绑定的严格许可。
3. 能将获准片段写成 `ConversationEvent + EvidenceLink + WorkCheckpoint` 的可追溯来源链。
4. 支持 Direct API 与 Agent-hosted 两种草案来源；后者可使用当前 Codex/TRAE 会话的推理，不要求 EOS 保存该客户端的 API Key。
5. 草案必须经人确认、改写、暂缓或丢弃；不会自动变成经验资产。
6. 只有来源、人工决策和成功结果齐全时，才允许升级为可复用 `ExperienceAsset`；失败与撞墙也会被保留为反思材料。
7. 有工作台、三灯注意力状态、macOS 本地入口、工作区预检和 Alpha 证据报告。

但它还不是成熟产品：目前只有小范围真实试验，尚无跨项目复用的真实收益证据，也没有低摩擦的各客户端原生安装体验。

## 4. 竞品不是一个产品，而是四类能力

| 类别 | 已有代表能力 | 它会替代 EOS 的什么 | EOS 仍需保留的差异 |
| --- | --- | --- | --- |
| AI 编程客户端 | Codex、Claude Code、Cursor、Copilot | 对话、写代码、项目规则、MCP 调用 | EOS 不与它们争“谁来写”，而记录跨客户端协作后哪些做法被证明有效。 |
| Agent 记忆层 | Mem0、Letta、OpenMemory、Cursor Memories | 长期偏好、检索、自动存取、跨会话上下文 | EOS 必须坚持“来源 + 人类判断 + 结果验证”，而非把被检索到的记忆当成事实。 |
| LLM 可观测/评测 | Langfuse、LangSmith 等 | Trace、token、工具调用、评测、数据集 | EOS 面向人的工作经验和后续复用决策，不只是开发者调试模型。 |
| 接入协议与工作流配置 | MCP、AGENTS.md、Rules、Skills、Hooks | 跨工具连接、指令、工具暴露 | EOS 提供经验资产的生命周期；MCP 只是接入总线，Rules/Skills 是经验可能导出的执行形态。 |

### 4.1 已被充分替代的部分

- “跨 AI 客户端接工具”：MCP 已经是公共协议，EOS 不应把它当护城河。
- “为 AI 保留长期记忆”：Mem0、Letta、OpenMemory 与 Cursor 的 Memories 已覆盖这一层。
- “项目规范和提示词持久化”：AGENTS.md、Cursor Rules、Copilot Instructions/Skills 已很成熟。
- “记录模型调用与评测”：Langfuse 已提供 trace、session、工具调用、人工标注与评测数据集。

### 4.2 仍未被完整替代的组合

EOS 的合理空位不是“又一个 memory MCP”，而是：

1. **跨客户端的本地经验边界**：同一个人可在 Codex、TRAE、Claude Code、终端之间工作，但经验只进入他明确选择的项目 Vault。
2. **把“提议”与“事实”拆开**：Agent 可以提出收据，不能直接把它提升为真理、偏好或 Skill。
3. **结果门槛**：可复用经验必须关联后续成功结果；没有结果时只是一份待证假设。
4. **人类可读的线性审查**：把非线性的协作过程压缩成“来源、主张、适用边界、反例、下一步”五个可判断项。

这不是不可复制的技术护城河。任何大模型客户端、记忆产品或可观测平台都可能加入它。它的潜在价值在于把这四件事做成一个足够低摩擦、足够可信的日常习惯，并积累经验证的经验网络。

## 5. 对当前产品最诚实的判断

### 有用，但只在一个窄场景里已经有用

对“长期做复杂项目、在多个 AI 工具间切换、会反复遇到相似工程决策、且愿意花 10 秒审查一次候选经验”的个人或小团队，EOS 已可以作为私有 Alpha 使用。它最实际的价值是：不会让重要的工程约束、失败原因和验证边界只留在某一个聊天窗口里。

### 还不能声称的价值

- 不能声称自动提升开发效率：尚无对照试验或真实时间节省数据。
- 不能声称经验会跨项目稳定复用：目前尚未有已验证资产和采纳反馈。
- 不能声称“兼容所有 AI 工具”：MCP 兼容不是自动接入；各客户端的项目级配置、权限和会话机制不同。
- 不能把 Marketplace、交易、定价当成近期核心：在未证明单个用户能形成高质量经验资产前，它们是过早扩张。

所以，今天的 EOS 是 **可信经验闭环 Alpha**，不是已完成的“AI 操作系统”，也不是一个可直接规模化售卖的 Skill 市场。

## 6. 当前哲学仍缺的五块拼图

1. **价值选择问题**：系统怎样知道什么值得成为候选？若全靠人点，摩擦太高；若全靠模型猜，噪声太大。需要“低风险自动暂存 + 人类批量确认”的提议层。
2. **结果归因问题**：一次成功往往由人、模型、代码库、环境共同造成。经验不能只写“成功”，应记录结果强度、证据类型与替代解释。
3. **经验保鲜问题**：技术栈、模型和项目会变。经验资产应有版本、适用环境、失效信号和复验机制，而非永久知识。
4. **审查成本问题**：人类审查若超过十秒，就会被绕过。必须把审查压缩为一个默认建议、一个风险点、一个可编辑主张和三种明确结果。
5. **边界路由问题**：当前 Codex 偏向全局 MCP 配置，项目切换仍有摩擦。EOS 必须维护“当前工具绑定哪个工作区”的可见状态，不能假装它已自动解决。

## 7. 现在应该砍掉什么，押注什么

### 暂停作为主线的内容

- Marketplace、支付、定价、排行榜；
- 大而全的“所有类型 Skill 自动生长”；
- 试图自动抓取全部聊天、终端或桌面活动；
- 把 EOS 发展成另一个聊天客户端。

这些不是永远不做，而是不应抢在核心价值被证明前做。

### 下一阶段唯一主线

**证明“经审查的经验能在下一次真实任务中被主动取回，并减少一次重复判断”。**

最小实验：

1. 选一个持续两周的真实项目，只接入一个主客户端和一个备用客户端。
2. 每次只允许产生一份候选收据；人用“确认、改写确认、暂缓、丢弃”处理。
3. 下一次相似任务启动时，EOS 仅展示已验证经验及其适用边界。
4. 人记录“采用 / 忽略 / 不适用”及一句原因；任务结束记录成功、部分成功或失败。
5. 对比没有 EOS 时是否重复解释约束、重复踩同一类坑、重复寻找历史决策。

成功标准不是资产数量，而是至少出现一次可追溯的链条：

`确认的收据 -> 观察到的成功结果 -> 已验证经验 -> 下一项目被采纳 -> 人确认它确实减少了重复判断`
