# Experience OS 3.3：外部体验 Beta 部署方案

日期：2026-07-27

## 1. 这次部署要验证什么

不是验证访问量，也不是把“上线”误说成产品成立。Beta 只验证三件事：

1. 新用户能否理解 EOS 的中心动作：把一次协作变成可审阅的经验收据；
2. 新用户是否愿意在真实项目中完成“证据 -> 收据 -> 结果 -> 复用试验”的最小闭环；
3. 复用试验是否真的减少下一次的重复判断，而非只增加记录负担。

## 2. 两种部署，不能混淆

### A. 公开展示页

目的：让任何人理解界面、概念和边界。数据只能是合成样例，所有写操作关闭。它收集的是可理解性反馈，不能收集真实协作内容，也不能被称为“多人工作台”。

### B. 邀请制真实 Beta

目的：让少量受邀者在自己的工作区体验完整闭环。每位用户必须拥有独立 Vault、独立许可与可撤销的访问身份；原始协作内容默认留在用户本机。中心服务只接收用户明确同意的、最小化的反馈和匿名化指标。

当前代码适合 B 的单用户/单 Vault Alpha，不适合把一个共享 Vault 直接暴露给陌生用户。因此不能跳过身份与租户隔离，直接把工作台公开上网。

## 3. 当前可执行的部署载体

仓库已提供 Docker 镜像构建与 Render Blueprint：

- `Dockerfile`：Node 20 + Git + 编译后的 React 工作台；
- `render.yaml`：单实例、`/var/data` 持久化磁盘、`/api/health` 健康检查；
- `npm run deploy:preflight`：在镜像或服务器启动前验证前端产物、Git 与持久化 Vault 路径。

服务新增 `POST /api/beta-feedback`：仅接受用户明确同意的产品反馈（阶段、清晰度、有效性、是否愿意继续使用、可选联系信息），字段有长度和枚举约束、单地址每小时最多 5 次。它不会接收或自动提取协作原文，也不会自动写入偏好、Skill 或经验资产。

选择单实例是当前 GitVault 的事实约束：文件系统型 Vault 需要持久化目录和单一写入者。Render 也说明持久化盘仅供单个服务实例使用，默认文件系统在重启/发布后不会保留数据。它适合作为受控 Alpha 的运行底座，不是多租户 SaaS 的最终架构。

## 4. 上线顺序

1. 用合成数据建立只读展示环境；
2. 选择 5-10 位受邀测试者，分别执行本机 Bootstrap；
3. 给每人一个独立的反馈入口，并记录是否完成首次收据、结果和复用试验；
4. 每周人工审查反馈，不自动把用户反馈写成偏好或 Skill；
5. 只有当多位用户完成有结果的复用试验后，才评估账号、团队空间和中心数据库。

## 5. 必须完成的发布前缺口

- 账号/会话与每用户独立 Vault 路由；
- 合成 Showcase 数据和只读 API 策略；
- 明示同意、删除请求、反馈字段最小化；
- 备份与恢复演练；
- 错误监测、速率限制与邀请管理；
- 真实用户反馈面板，且不能混入演示或模拟交易数据。

这些是外部体验的安全前提，不应为了更快公开而绕过。
