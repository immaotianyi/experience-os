# Experience OS 3.1：可用产品构想与 Alpha 计划

日期：2026-07-19  
状态：作为后续开发的产品约束

## 1. 先把产品说清楚

### 一句话

**EOS 是给 AI 协作型开发者的“经验收据系统”：它把一次真实工作中被验证过的做法，连同证据、边界、人的判断和结果，变成下一次可以谨慎复用的经验。**

它不是：

- 泛化聊天助手；
- 监控用户所有应用的工具；
- 自动保存一切对话的记忆库；
- 以 Skill 数量和下载量为目标的市场；
- 让 AI 绕过人做发布、删除或权限升级的代理。

它解决的具体痛点是：

> 用户和 Codex 在一个项目里已经花时间摸清了架构、踩过坑、确定了测试方式；下一个相似任务却又要从头解释，且无法判断上次的做法到底是在什么条件下有效。

EOS 的答案不是“我记住了”，而是“这是一条已经被验证过的经验；它来自哪里、适用什么、有哪些反例、上次结果怎样，都在这里”。

## 2. 只服务一个第一用户

### Alpha 用户

使用 Codex/Claude Code/Cursor 开发软件的独立构建者：

- 同时推进 2-5 个代码项目；
- 经常与 AI 长对话、反复试错；
- 愿意在关键节点花 15-30 秒确认一次经验，但不愿手工维护知识库；
- 在乎本地数据、可追溯性和工程验证；
- 第一阶段不假设团队协作、付费市场或跨设备同步。

### Alpha 的承诺

经过三次真实项目使用后，用户至少应能说清：

1. EOS 记录了哪三条对我有价值的经验；
2. 每条经验的来源和验证结果；
3. 下一次工作时，EOS 至少避免了我一次重复解释或重复踩坑。

如果这三件事做不到，市场、团队、自动化交易都没有意义。

## 3. 用户第一天的真实流程

```mermaid
flowchart LR
  A["在现有项目执行 eos bootstrap"] --> B["继续在 Codex 正常工作"]
  B --> C["到达一个工作节点：方案确定/测试通过/撞墙"]
  C --> D["用户或 Codex 提交一段已同意的协作证据"]
  D --> E["EOS 生成一张 Draft Experience Receipt"]
  E --> F["人用 15 秒：确认、改写、暂缓或拒绝"]
  F --> G["生产动作与测试结果进入 Outcome"]
  G --> H["满足条件才升级为 Verified Experience"]
  H --> I["下一项目开始时仅建议相关经验"]
```

### 具体例子

用户在 Codex 中修复登录问题，经过三次尝试后确认：`token 刷新必须先检查服务端时钟偏差；仅前端重试会掩盖问题`。

1. 用户完成一次测试后，选择“保存这段协作”；EOS 记录关键对话、Git commit、测试命令和结果为证据。
2. EOS 提出草稿：发生了什么、证据是什么、适用边界是什么、尚有什么不确定性。
3. 用户只需要补充或确认一句：`仅适用于 OAuth refresh flow`。
4. 结果记录为测试通过和线上观察；用户确认该决策。
5. EOS 将其升级为已验证经验。
6. 下次用户开始相似认证任务，EOS 显示一张建议卡，而不是把旧内容无声塞入上下文。

## 4. 第一版只需要四个界面状态

当前工作台保留高级控制台，但 Alpha 主界面必须收束为以下四个状态：

| 状态 | 用户看到什么 | 用户能做什么 | 系统不能做什么 |
| --- | --- | --- | --- |
| `现在工作` | 当前目标、自治等级、最新证据 | 捕获片段、添加文件/测试证据 | 自动读取其他应用或自动写入业务代码 |
| `待确认收据` | 一张线性卡：主张、证据、边界、不确定性、选项 | 确认、改写、暂缓、拒绝 | 直接升级为已验证经验 |
| `验证结果` | 本次决策、测试/交付结果、失败与墙壁 | 记录结果、关联测试、回退决策 | 把失败隐藏为“成功记忆” |
| `下次可用` | 仅与当前目标相关的已验证经验 | 查看来源、采用、忽略、标记不适用 | 静默注入或自动执行 |

这四个状态对应人的线性认知过程：**现在发生什么 -> 我是否认可 -> 结果如何 -> 下次是否值得用**。

## 5. 3.1 的核心对象与严格关系

```text
ConversationEvent / GitDiff / TestResult
                -> EvidenceLink
                -> Draft ExperienceReceipt
                -> DecisionReceipt (human reviewed)
                -> OutcomeRecord
                -> ExperienceAsset (approved)
                -> ReuseSuggestion (next project only)
```

### 不可破坏的规则

1. 没有 `EvidenceLink`，不能声称有经验。
2. 没有人工审查的 `DecisionReceipt`，不能升级。
3. 没有真实 `OutcomeRecord`，不能称为已验证。
4. 失败、反例和边界与成功经验同等重要。
5. 复用永远先是建议；进入执行需要当前项目的 `ExecutionPolicy`。
6. 捕获必须有用户同意，撤销同意应停止未来捕获与复用。

## 6. 已完成、下一步和暂不做

### 已完成：可信核心

- 本地 Git Vault、项目、证据、收据、决策、结果、经验资产；
- 引用完整性、跨项目引用拒绝、显式同意捕获；
- `explore / advise / draft / execute / commit` 的 AI 写入策略；
- 人工审查和成功结果是 ExperienceAsset 升级门槛；
- React 项目工作台；
- `.eos/` Bootstrap 与 MCP Capture Relay。

### 3.1-A：让“捕获”少打扰人

目标：从手动填写多张表单，变成一次“保存这个工作节点”。

1. 新建 `WorkCheckpoint`：用户点击一次即可选择对话片段、Git diff、终端输出或测试结果作为候选证据；
2. MCP 增加受限的 `eos_capture_checkpoint`，由调用方显式传入材料和同意范围；
3. Project 页面将“捕获、证据、Receipt”收敛为一个顺序流；
4. 一次捕获默认只创建 Draft，不自动升级。

**验收**：用户在 30 秒内完成“证据 -> Draft Receipt”；不必理解 Vault 或 JSON。

### 3.1-B：让“收据”真的从协作里长出来

目标：接入真实 LLM，但只用于提炼草稿。

1. 用 LLM 从已同意的证据生成 `DraftReceiptProposal`；
2. 草稿必须逐条附来源引用，并显式输出：主张、反例、边界、不确定性；
3. 人只能确认、编辑、暂缓或拒绝；
4. 每次编辑都成为以后改进提炼质量的反馈，不直接变成永久偏好。

**验收**：三位用户中，至少两位认为草稿“比从零写总结更省事”；每张卡都能在 30 秒内处理。

### 3.1-C：让“复用”成为可测帮助

目标：开始新项目或新任务时，EOS 给出一条克制建议。

1. 用户输入项目目标或任务描述；
2. EOS 只从 `approved ExperienceAsset` 中检索，最多给出三条；
3. 每条建议展示来源、适用边界、上次结果和“采用 / 忽略 / 不适用”；
4. 记录采用后的人工改写、测试结果和撤回原因。

**验收**：三次复用尝试中至少一次被用户保留；所有错误建议都可解释为何匹配错误。

### 暂不做

- 多人实时协作和云同步；
- 真实支付、市场、定价；
- 自动读取完整屏幕、完整对话历史或任意本地文件；
- 自动发布、自动修改生产环境、自动提升权限；
- “人格画像”或永久偏好标签。

## 7. 四周 Alpha 推进表

| 周次 | 交付物 | 真实验证 |
| --- | --- | --- |
| 第 1 周 | WorkCheckpoint + 主界面收敛 | 自己用 EOS 记录本项目的一次工程决策 |
| 第 2 周 | 真实 LLM Draft Receipt + 编辑/拒绝记录 | 三个真实工作节点，比较手写与草稿耗时 |
| 第 3 周 | 已验证经验检索与 ReuseSuggestion | 在新任务中试用至少三次建议 |
| 第 4 周 | 复盘仪表与首批用户试用包 | 3 位 Alpha 用户、每人 1 个项目、访谈与数据复盘 |

## 8. 不靠感觉判断成败

### Alpha 成功指标

- `Receipt processing time`：从出现卡片到处理完成的中位数小于 30 秒；
- `Evidence coverage`：被确认的 Receipt 中，100% 可回到至少一条来源；
- `Verified experience rate`：不是越高越好；重点是每一条升级都符合完整链路；
- `Reuse usefulness`：至少 30% 被展示建议被采用或明确标为“以后可用”；
- `Wrong reuse`：错误建议必须低于 20%，且每次都记录原因；
- `Trust`：未授权捕获、未授权写入、无来源升级均为 0。

### 应暂停或转向的信号

- 用户持续不愿意在工作节点花 15 秒确认；
- Draft Receipt 需要大量重写，且比手写更慢；
- 检索建议常常不相关，用户宁愿关掉它；
- 捕获范围让用户感到不舒服或不愿授予同意。

这些不是“用户教育不足”，而是产品应减少干扰、收窄场景或改变提炼方式的证据。

## 9. 当前最重要的产品决策

> **EOS 3.1 的唯一北极星不是“积累多少 Skill”，而是“用户下一次相似工作时，是否因一条可验证经验少走了一段弯路，同时仍能理解和控制系统”。**

因此，接下来工程优先顺序固定为：

1. WorkCheckpoint；
2. Draft Receipt；
3. ReuseSuggestion；
4. 真实项目评估；
5. 只有证明有效后，才扩团队、市场与复杂自治。
