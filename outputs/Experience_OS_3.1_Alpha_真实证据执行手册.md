# Experience OS 3.1 Alpha：真实证据执行手册

## 1. 这次 Alpha 要回答什么

不是“EOS 的功能是否存在”，而是以下三个可被证伪的问题：

1. 用户能否在不被背景监控的前提下，把一次真实的人机协作保存为可回看的工作节点？
2. 真实模型生成的草案，是否帮助用户更快、更准确地形成自己的经验收据，而不是诱导用户接受模型结论？
3. 一条经过结果验证的经验，能否在另一个项目中被有边界地采纳？

任何一个答案为否，都是有效结果。不要为了完成指标而把草案全部确认，也不要把失败结果改写为成功。

## 2. 开始前：每位试用者一次性准备

1. 选择自己的真实工作目录，运行：

```bash
npm run bootstrap -- /你的/工作目录 "项目名称" "本次真实目标"
```

2. 配置有余额的真实模型提供商。当前支持：

```bash
LLM_PROVIDER=deepseek DEEPSEEK_API_KEY=...
# 或 openai / anthropic
```

3. 启动隔离工作台：

```bash
npm run workbench -- /你的/工作目录 4180
```

4. 只在用户看过完整内容并同意时，使用严格许可捕获外部协作。不要把密钥、客户数据、个人信息或不该外传的代码片段提交给外部模型。

## 3. 三项目最小实验

### 项目 A：捕获与草案

- 选一个 20-60 分钟内确实要完成的小任务，例如定位一个 bug、完成一段产品判断或整理一次研究结论。
- 任务告一段落时保存 **1-3 个工作节点**；每条都要说明来源、发生的事实和仍未解决的问题。
- 记录一个人工基线：若不用 EOS，你预计需要几分钟才能把这段工作整理给未来的自己？这只是自评，不是事实指标。
- 生成一份真实模型草案。人类必须选择：直接确认、改写后确认、暂缓或丢弃。
- 执行：

```bash
npm run alpha:evidence -- /项目A目录
```

通过条件不是“确认草案”，而是报告出现至少 1 条 `live` 草案和 1 次明确的人类处理。

### 项目 B：结果验证

- 对项目 A 的确认收据写下一个具体决策，并在真实工作中执行或观察其结果。
- 结果可以是 `success / partial / failure`；如为 partial 或 failure，要写明实际观察，而不是只写“感觉不好”。
- 只有 `success` 且被人工审查的同一条决策，才可升级为 ExperienceAsset。
- 再运行 `alpha:evidence`，检查 `successfulOutcomes` 与 `approvedAssets`。如果无法升级，保留系统给出的缺口。

### 项目 C：跨项目复用

- 新建一个与 A/B 有一定关联、但不是同一任务的项目。
- 查看 EOS 提供的已验证经验建议；系统只能建议，不会自动套用。
- 人类选择采纳、忽略或不适用，并写下简短原因。
- 运行 `alpha:evidence`。只有跨项目出现 `adopted`，才可以说“发生过一次复用”；这不等于已证明普遍价值。

## 4. 结束时需回收的证据

每个项目提交以下四项，允许脱敏：

1. `npm run alpha:evidence -- <workspace>` 的 JSON 输出；
2. 试用者的基线时间估计、EOS 实际操作耗时，以及二者都只是自报的数据说明；
3. 草案的人类处理结果和理由：确认、改写、暂缓、丢弃各自为何发生；
4. 最不舒服、最容易误解或最让人不信任的一步。

不要回收 API Key、未脱敏协作原文或业务文件。EOS 的设计目标是留下经验的边界与证据，而不是把用户工作变成数据源。

## 5. Alpha 后的判定

可以进入下一轮改进的最低证据为：

- 3 位试用者各完成至少 1 个项目；
- 至少 3 条真实模型草案，且都有明确人类处理；
- 至少 1 条成功验证并升级的经验资产；
- 至少 1 次跨项目采纳或明确不适用反馈；
- 对许可、草案、审查、结果、复用五步中的失败均有保留记录。

达不到不等于失败。它意味着 EOS 的假设尚未成立，下一轮应优先修复出现频率最高、后果最重的断点，而不是急着增加功能。
